### 1.2 三处必须修正的解读

**修正 1：run5 不是"过拟合治好了"，是"什么也没学会"。**

`out/run5/eval_train.json`（**模型见过的 800 条**）：

| 任务 | 训练集成绩 | 不动脑子的参照 | 判定 |
|---|---|---|---|
| will_merge | AUC 0.5862 | 0.5 | 勉强有信号 |
| review_route | macro-F1 0.2623、准确率 0.2525、平均置信度 **0.2583** | 一律答 normal 0.5363；均匀分布置信度 0.25 | **比常数差，输出≈均匀分布** |
| change_scale | MAE 0.8012 | 均匀分布期望值 MAE ≈ 0.8 | **等于没读数** |

同一模式在 dev（`eval_dev.json`）和 test（`eval_test.json`）上重复，route 平均置信度 0.2584 / 0.2573。

**关键：route 和 scale 的标签是确定性规则**（`task.py:105-123` 的 `route_policy`、`task.py:91-102` 的 `churn_bin`），**而它们的输入原文就印在 state 里**（`build_dataset.py:82-86` 的 `files changed` / `lines: +a -b` / 文件列表）。也就是说这两个任务的"可学上限"是 100%，模型在自己的训练集上却"比一律答 normal 更差"。

→ 这不是标签难、任务难、数据不够，是**信息没进去 或 目标函数没在优化这件事**。这也是为什么验证要排在训练前面。

（顺带：`任务文档.md:279` 那条"管线没问题、模型能学"是建在仓库名泄漏上的，随修正 1 一起作废。）

**修正 2："数据不是杠杆"的那条证据不可比。**

0.541 那次评测的测试集是 **29 条**（`out/run2/eval_test.json:3` 的 `n_cases: 29`），0.525 那次是 **434 条**（`out/run3/eval_final_test.json:3`）。29 条的 AUC 误差棒约 ±0.15~0.2，两个数不可比（文档自己也写"测试集比迁移前的 29 条大了 15 倍"，`任务文档.md:104`）。

→ **"先加数据没用"这个结论仍然成立，但要换成轮次证据**：同一份数据 5 轮 vs 10 轮，test 0.5551→0.5245（`任务文档.md:275`），加上训练集欠拟合。"数据量已饱和"这句话降级为 **【未核实】**。

**修正 3：结论 2（路由平衡改过头）的归因是混淆的。**

run3→run5 同时改了三件事：去仓库名、路由平衡、早停判据（`任务文档.md:295-299`）。而 `normal` F1 0.66→0.22 的比较正好横跨这三处改动，所以"是平衡改过头"和"是没了泄漏之后 route 本来就退步"分不开。

同时 run5 的 route 数字**恰好等于"输出均匀分布"会得到的数字**（四类最大概率均值 0.2573，四选一均匀是 0.25；四个类 F1 挤在 0.06~0.24，`eval_test.json:22-27`）。所以 0.1852 这个数里"平衡策略"占多少，是未知的 —— 先用验证 V3 判一下。

### V0 可比性检查（5 分钟，不用 GPU）

- **目的**：确认跨轮对比用的是**同一份** 434 条测试集。现在这只是文档断言：meta.json 里没有任何哈希字段，全项目没有 hashlib/sha256。
- **做法**：
  ```powershell
  Get-FileHash data\ds3\test_cases.jsonl, data\ds5\test_cases.jsonl -Algorithm SHA256
  ```
  之后每建一版数据集（ds6/ds7…）都把 test 的哈希记进 meta 或单独的 `out/` 记录里。
- **判据**：ds3 与 ds5 的哈希相同。**不同 → 之前所有跨轮对比作废**，先查为什么。
- **通过后**：在 v2 的每条评测结论后面都带上这个哈希。

### V1 确定性标签的可学性基线（15 分钟，不用 GPU）

- **目的**：证明 route/scale 的信息确实在输入里，把矛头从"标签难"拧到"管线/目标函数"。
- **做法**：对 `data/ds5/train_cases.jsonl` 每条 case，用 raw 的 `files/additions/deletions` 直接算 `route_policy` / `churn_bin`，与 `train_items.pt` 里的 label 对拍；再单独看"文件数 > 40"（文件列表被截断）的那一批。
- **输出**：标签一致率（期望 100%）、以及"只用 state 里 `lines:` 那一行做正则解析再分箱"的 MAE（期望 0）。
- **判据**：100% 一致且正则 MAE≈0 → 信息在输入里，**问题在管线/模型**；<100% → 先修标签生成链路，别谈模型。
- **说明**：12/12 抽样对拍的是"标签 vs GitHub 接口"（`任务文档.md:22`），**没做过"标签能否由 state 文本恢复"这一步**。
- **需要**：一个约 30 行的脚本（建议 `tools/v_tags.py`）。【待创建】

| 测什么 | 结果 |
|---|---|

而 `will_merge` 主要靠 diff 判断 —— 所以要优化的是"把预算从 `description` 挪给 diff"。

**原始假设（仅作记录，已不成立）**

- **目的**：验证假设 —— **`description` 没有长度上限、`lines:`/文件列表排在它后面、diff 又在最后，而总预算只有 1024 token**（`build_dataset.py:75-87`、`ds5/meta.json:4`）。长正文会把 route/scale 依赖的两行挤掉；同时 `make_items` 在选项被砍时**整条丢弃**（`build_dataset.py:110-112`），被丢掉的恰恰是最长的 PR（改动≥400 行 或 文件≥10 → 正是 `block` 类）。
- **做法**：① 统计每条 state 的 token 长度分布与截断比例；② 检查截断后 `lines: +` 是否还在；③ 统计被丢弃的条数、以及这些 case 的 route 标签/churn 分布。
- **判据（原定）**：截断率、丢弃率都 <1% 且丢弃条目的 route 分布与总体一致 → 假设不成立，转 V5。→ **实测正是这个结果。**

### V3 逐条概率体检 + 先验还原（20 分钟，需要一次 434 条推理）

- **目的**：分清"模型不会分四类"和"判定规则被训练先验压住了"。
- **做法**：
  ```powershell
  & $PY -u -m src.batch_predict --ckpt out/run5/final --cases data/ds5/test_cases.jsonl `
      --compare-rule --top 0 --out out/run5/percase_test.jsonl
  ```

- **判据**：还原后 macro-F1 明显 >0.1852（比如 ≥0.24）→ **是判定规则问题**，M1 的紧迫性下降、M4 变成必修关键项；没有改善 → 模型确实没在排序，M1 必须连 V5 一起做。
- **需要**：一个约 30 行的脚本（建议 `tools/v_prior.py`）。【待创建】
- 顺带：`batch_predict.py:169-215` 本来就能输出含 `route_probs`/`p_merge` 的 JSONL —— 这条同时也验证了 D2（逐条输出）不需要新功能，只需要接进常规路径。

### V4 按仓库拆分评测（10 分钟，不用 GPU）

- **目的**：验证 "0.5766" 是不是两个仓库平均出来的假象。
- **做法**：把 434 条按 repo 拆两半，分别算 will_merge AUC / route macro-F1 / scale MAE。
- **判据**：两仓方向一致、量级接近 → 可以用合并数报；**两仓相反 或 相差 >0.1 → 以后所有结论必须分仓报，且"提升 0.02"这类判据彻底不可用**（要改评测协议，见 S1）。
- **需要**：一个约 40 行的脚本（建议 `tools/v_byrepo.py`）。【待创建】

### V5 目标函数体检（20~30 分钟，需要几行代码）

- **目的**：确认 `rlcd_loss(..., group_size=4, sigma=0.4→0.1)`（`train.py:436`、`406-419`）到底有没有在优化我们要的东西 —— 评测用的是 argmax 准确率和期望值 MAE，而它优化的是"相对偏好"。一个只优化偏好的损失，输出接近均匀分布是自然结果（正好对上置信度≈0.25）。
- **做法**：`--limit-items 200 --epochs 2 --no-early-stop` 跑两次：一次原样，一次临时加一路普通交叉熵（scale 用期望值损失）；比较训练集上的 route macro-F1 / scale MAE。
- **判据**：加 CE 后训练集指标明显跳升 → **原来的目标函数没在拟合标签**，M3 要连带改训练目标；没差别 → 转 V2 的方向（更可能是信息没进去）。
- **需要**：现有 CLI 没有这个开关，要几行代码。【待写】

### V6 噪声下限（30 分钟，**由"可选"上调为"必做"**，用 GPU）

- **目的**：知道"换 seed 会波动多少"，否则没法给"提升多少算有效"定线。
- **做法**：同一配置（小规模或全量）换 2 个 seed 各跑一次，比 test 的三项指标。
- **判据**：如果波动 ±0.02 → **所有小于 0.03 的差异都不能当结论**；这直接否掉 v1 里"Round B 提升 <0.02 就放弃扩数据"的判据。

## 四、必修 M（训练前必须改对）

> 一共 4 项代码/机制改动 + 2 条纪律。**拆成两跑**，一跑约 2 小时（每轮 450~500 秒，10 轮；**代码里没有 patience，不会自动提前结束**）。

### M1 路由平衡调温和（改 `balance_route_items()`）

- **改什么**：把"拉平到最大类"改成温和版，**并加"不下采样"守卫**：
  - 目标写成 **每类 `target_c = max(原条数, 2.5 × 最小类)`**；
  - 或者保留单一 target，但把乘数改成 `mult = max(1.0, min(cap, target / len(group)))`；
  - 必须**打印每类前后条数**（现在只打印目标值，看不出有没有被下采样，`build_dataset.py:167`）。
- **为什么**：**【已核实】** `build_dataset.py:155-165` 的结构是 `mult = min(cap, target/len(group))`；若把 target 直接改成标量 552，`normal` 的 `mult=0.417 → whole=0 → frac>0` 走 `group[:round(1324*0.417)]`，**只取 552 条**。这与 v1 要求的"只上采样、不下采样"相反，且会让实验结论被彻底误读。
- **验收**：日志里 `normal` 仍 ≈1324、其余三类 ≈552，route items 总数 ≈2980。
- **【未核实】** `fast_track`/`block` 的原始条数：任何可读文件都没有（只在 UTF-16 日志里）。硬约束是两者之和 = 965；要得到 552/552 必须两者都 ≤552。

### M2 把预算从 `description` 挪给 `diff`（**已降级为可选优化**，原写的是"必修第一条"）

- **为什么降级**：原理由（"长正文把 route/scale 依赖的字段挤出去"）已被实测推翻 ——
  那些字段的保留率 **99.9%**、丢弃样本 **0 条**（§1.0 的 E1/E2）。信息确实在输入里。
- **新理由（这条仍然成立）**：**64.1%** 的样本被截断到 1024 token，砍掉的正是排在**最后**的 diff，
  而 `will_merge`（会不会被合并）主要靠 diff 判断 —— 应该把预算让给 diff。
- **改什么**：给 `body`（`description`）加长度上限（建议 **500~800 字符**，现在最多 1500），
  或者把 `description` 挪到 `files changed / lines / 文件列表` **之后**；
  **不动 diff 的截断策略**（保证训练与推理一致）。
- **口径一致性**：`build_state` 是唯一的拼装点，训练/评测/预测共用（`build_dataset.py:56`
  注释已声明这个设计），所以**只改一处**，三处口径自动一致。
- **验收**：`diff:` 的实际保留长度中位数明显上升，且 `will_merge` 的 dev AUC 不低于改动前。
- **优先级**：排在 M1 / M3 / M4 之后，随第二跑一起做或单独一跑。

### M3 记录与选轮机制（替代 v1 的复合早停标量）

- **改什么**：
  1. `eval_items()` 补算 route 的 **macro-F1**（可直接复用 `evaluate.py:58` 的 `macro_f1`），每轮打印 will_merge AUC / route macro-F1 / route 准确率 / scale -MAE **四项**（A3 保留，且它比 A2 有用）；
  2. **每轮存"只含可训练头"的 checkpoint**（约 26.5M 参数，约 53MB/轮），而不是整份 `state_dict`（现在 `save_ckpt_dir` 存的是整份，含冻结编码器，`train.py:180-201`）；
  3. **不新增 `composite` 标量**。理由：结论 3 的问题是"只用 will_merge AUC 挑轮把 route/scale 还在改善的轮次砍掉了"（`任务文档.md:328-331`），那就别把选择压成一个数 —— 存了每轮的头 + 每轮指标，事后想用什么规则挑就用什么规则挑，不用为换判据再跑一次。
- **如果仍想用 `--early-stop-metric composite`，必须**：(a) 把 `composite` 注册进 `EARLY_STOP_METRICS`（`train.py:173-177`），否则 argparse 的 `choices`（`train.py:265`）会当场拒掉；(b) 注意 scale 键是 `neg_score_mae`（`train.py:239`，**已经取过负号**），复合式里符号别写错；(c) 三项量纲不同（AUC 波动 ~0.1、macro-F1 ~0.12、`1−MAE/4` ~0.04），**等权≠等影响**。
- **顺带纠正**：现在这套"早停"只是每轮存 `best/` 并在最后回退（`train.py:488-523`），主循环 `for epoch in range(start_epoch, args.epochs)` **没有 patience**，永远跑满 `--epochs`。想要真提前结束，要单独加 patience 参数。

### M4 判定规则跟先验一起改（不只 will_merge）

- **改什么**：
  0. **先修一个评测代码 bug（本轮升级为必修，来自 §1.2 修正 4）**：`evaluate.py:151` 的
     `best_threshold_accuracy` 现在是在**被评测的那个划分上**挑最优阈值 ——
     用 `--split test` 跑就等于**拿测试集调参**，报出来的"最优阈值准确率"必然偏乐观
     （v1 里那个"最优阈值 38.7%"就是这么来的）。改成**在 dev 上挑阈值、再套用到 test**，
     或者只报阈值无关的 AUC。**不修这条，后面所有"最优阈值"数字都不能信。**
  1. will_merge：用 **dev** 定阈值（D1），并按真实先验重加权后定，不能直接搬 50/50 的 dev；
  2. route：argmax 前做**先验修正**（除以训练先验、乘上目标先验）；
  3. scale：期望值也按先验修正后再取整。
- **为什么**：M1 主动改了训练先验，不配一条判定规则，argmax 会再错一次；
  V3 会给出"这一步能救回多少"的量化。
- **口径**：阈值只能来自 dev，test 只在最后一次用一次；跨轮比较必须同口径。

### 纪律 1：变量隔离（一次只改一件事，拆成两跑）

- 第一跑：**只改 M2 + M3**（state 顺序 + 记录/存头）。
- 第二跑：在这一跑基础上**再加 M1 + M4**（平衡 + 判定规则）。
- **为什么**：run3→run5 同时改三件事，导致结论 1、2 的归因全是混淆的（修正 3）。两跑共约 4 小时，换来的是可解释的结论。

### 纪律 2：评测口径固定

- dev 选轮；**test 只在最后一次报**；报的时候**按仓库分组**（V4 的结论决定是否必须）；
- 每次报告里同时记：配置 / seed / 数据集哈希（V0）。

### 必修的命令骨架（**只是骨架，M1~M4 改完才有效**）

## 五、选修 S（按验证 + 必修的结果决定，先做哪个看第六节）

### S1 修评测口径（**建议第一优先，成本最低**）

- **做什么**：① 22 个仓 → **按仓库分组的 K 折**（比如 5 折、每折留出 4~5 个仓）；② 至少把现在 test 的 2 个仓**分开报**；③ 配对自助法改成**按仓库聚类重采样**（现在是按 PR 重采样，会低估不确定性）；④ 把"最小可检测差异"写死；⑤ 给测试集加哈希并冻结，改测试集就换版本号。
- **为什么**：434 条 / 2 个仓撑不起 0.02 级判据 —— 文档自己算出的 +0.052 AUC 的 95% 置信区间是 `[−0.0001, +0.1245]`，一侧 p≈0.025（`任务文档.md:317-318`）。
- **成本**：主要是写评测脚本，不训练。

### S2 扩数据（原 Round B）—— 触发条件放宽、结论口径收紧

- **触发**：S1 做完（否则判不了）+ 必修达标。
- **注意**：3705（22 仓）→ 9951（49 仓）同时改了**数据量**和**仓库数**（`ds5/meta.json:6-29` vs `任务文档.md:90`），所以只能得出"更多仓库的更多数据"，**不能得出"数据量饱和"**。
- **判据**：在 S1 的新协议下，差异必须大于最小可检测差异，否则写"**无结论**"，不写"放弃扩数据"。

### S3 换 `review_route` 的标签来源（原 C1）—— **排到最后**

- **前置**：V1/V2/V5 都没有支持"是标签的问题"。
- **四类必须先互斥化**（v1 的定义有洞）：`fast_track`（合并前 0 条评论且 <24h）与 `normal`（1~3 条评论）漏掉"≥4 条评论"和"0 条评论但 >24h"；`needs_tests` 与 `normal` 重叠；`block` 与"合并了但中途被要求改"重叠。要写明**优先级顺序**或加一个 other 桶。
- **缺料清单（必须先补，否则算不出来）**：`raw_v2.jsonl` 里**没有 `merged_at`、没有 `state`**；`review_comments/comments/commits` 实测**全为 0**；`--with-reviews` 虽然存在（`mine_github.py:497-498`），但只取 `/pulls/{n}/reviews` 的 `state`、**无分页**（单 PR 超 30 条被静默截断），也没有 `/pulls/{n}/comments` 端点。所以 v1 表里的"合并前 0 条 review 评论""1~3 条评论""从创建到合并 <24h"**目前一个都算不出来**。
- **成本（重估）**：补 reviews 最低约 **1.0 万次**请求，含 diff 回落约 **1.3 万~1.7 万次 ≈ 2.0~3.4 小时**（不是 1 小时）；**沿用旧 `--out` 会被 seen 全部跳过、一条 reviews 都不抓**（`mine_github.py:559-569`、`419-421`），必须换新输出文件或加"只补 reviews"模式。
- **口径提醒**：语料只含 `state=closed`（`mine_github.py:397`）且原始挖掘带了 `--min-open-hours 1`，**1 小时内关闭的 PR 已被排除** → `fast_track` 会系统性偏少，类别定义要基于实际语料重划。

### S4 换 `will_merge` 的任务定义（原 C2）—— 与 S3 合并

- **为什么合并**：C1/C2 用的是**同一批 review 事件**（有没有 review、有没有被要求改），挖一次、两个标签一起做，省一轮。
- **提醒**：`reject` 和"被放弃（abandoned）"不是一回事 —— 先统计"被关闭的 PR 里有多少有维护者互动"，互动率很低就说明 `reject` 不是一个真实类别。
- **任务定义层面的问题**：语料只有已关闭的 PR，而真实用途是对**刚打开的 PR** 判断，两者人群不同，写清楚再决定。

### S5 在目标仓库自己的历史上微调 + 历史合并率先验（原 C3）

- **我同意这是最可能真正有用的一条**，而且代码里留了口子（`build_dataset.py:54-56` 的注释写的就是这条路，把 `ANONYMIZE_REPO` 改回 `False` 即可）。

- **实现面**：`mine_github.py` 支持 `--repos owner/name` 限定单仓（`490-491`）；但合并率先验在 `src/` 里**没有实现**，只有离线脚本 `out/_repo_baseline.py`。
- **参照物**：先用查表基线本身当基线 —— 只用"这是哪个仓库的历史合并率"，dev AUC **0.8376**（`任务文档.md:254-256`）。微调后的模型要**打过它**才算有用，而且要**按仓库分别报**。
- **样本量**：单仓几百条起步，评测要按时间切分 + 多次重复。

## 六、门槛怎么写（回答 v1 的问题 2）

**v1 的写法要改三处**：

1. **不要三个阈值同时满足才算过关**（v1 的 1.3、Round A 判定表）。在 434 条 / 2 个仓的评测上，三项合取的检出力很低。改成 **一个主指标 + 其余两项"不许变差"的非劣门槛**。
2. **主指标应该由用途反推**。如果输出是"给 200 个 PR 排序、我只看前 20%"，主指标就该是 **top-20% 的精确率/召回率**，AUC 0.70 本身跟"有没有用"没关系。
3. **参照物要换**。现在只有"常数基线"，但文档自己已有更强的参照：**查表基线 dev 0.8376**（`任务文档.md:254-256`）。所以 "AUC ≥ 0.70" 在仓库内场景下**低于**一个五分钟能写出来的基线；而在跨仓库场景下 0.70 又贴着计划自估的天花板 0.70~0.78（v1 的 4.C2）—— 两个说法自相矛盾，要按场景分开写。

**如果暂时仍用指标当门槛，我建议这样定（你可以改）：**

| 任务 | 必修 M 的过关线 | 理由 |
|---|---|---|
| will_merge | AUC ≥ **0.65**（非劣 0.5766） | 0.70 贴着自估天花板；0.65 是"先证明跨仓有信号" |
| review_route | macro-F1 ≥ **0.30**（非劣 0.1852） | 先超过 run3 的 0.2634 且**不靠泄漏**；0.45 留作终局目标 |
| change_scale | MAE ≤ **0.70**（非劣 0.8185） | 回到 run3 的 0.6952 水平；0.40 留作终局目标 |

**另加三条**：
- **有效性门槛（并由此把 V6 从"可选"上调为"必做"）**：任何差异必须大于 V6 测出的噪声下限；
  没有 V6 的话，**<0.05 的 AUC 差异一律记作"没变化"**。这条现在是硬前置 ——
  上面那张过关线表里每个数字都依赖"多大差异算有效"，而 V6 是唯一能给出这个数的实验。
- **参照物按场景分开**（v2 已指出，这里再钉一下）：仓库内场景的参照是 **查表基线 dev AUC 0.8376**，
  跨仓库场景的参照才是常数基线。两套门槛不能混着用。
- **代价不对称**：现在全文没有一处写"漏判 block"和"误判 block"的代价。路由这类门禁
  应该由代价反推（比如"block 的漏报率 ≤20%"），而不是由指标好看程度决定。
