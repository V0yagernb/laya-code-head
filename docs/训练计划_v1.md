## 二、下一轮（Round A）：验证方法修正，**先不动数据**

### 为什么先不动数据

第 4 条结论：数据不是当前瓶颈。Round A 的目的是**确认方法改对了**，
所以**只用 3705 条**（跑得快、只有 1.5 小时），把"方法"当成唯一变量。
方法确认有效之后，Round B 再上 9951 条 —— 顺序反了就是浪费 4 小时。

### Round A 要改的三处代码

| # | 文件 | 改什么 | 具体做法 |
|---|---|---|---|
| A1 | `src/build_dataset.py` | **路由平衡调温和** | `balance_route_items()` 里把目标从"拉平到最大类"改成 **`target = 2.5 × 最小类条数`，且只上采样、不下采样**。按现在的分布会变成 `normal 1324 / fast_track 552 / block 552 / needs_tests 552`（比例 2.4:1，而不是 6:1） |
| A2 | `src/train.py` | **早停改用复合判据** | `eval_items()` 里补算 route 的 **macro-F1**；新增判据 `composite = mean(AUC, macro-F1, 1 − MAE/4)`（三项都落在 0~1，等权相加，简单可解释）。`--early-stop-metric composite` |
| A3 | `src/train.py` | **每轮多打印几个指标** | 现在只打三个，加上 macro-F1，方便判断"这一轮到底是哪个任务在变好/变差" |

**保持不变**：`ANONYMIZE_REPO = True`（结论 1 已验证有效）、测试集两仓不动、冻结 encoder。

### 执行命令（我按这个跑，你可以改参数）

```powershell
$PY="<VENV>\Scripts\python.exe"
cd <PROJECT_ROOT>

# 1) 重建数据集（同一批 3705 条，只改平衡策略）
& $PY -u -m src.build_dataset --raw data/raw_snapshot.jsonl --out data/ds6 `
    --model-id models/laya --test-repos encode/httpx,python-poetry/poetry `
    --balance --balance-routes

# 2) 训练（早停判据用复合指标）
& $PY -u -m src.train --ds data/ds6 --out out/run6 --model-id models/laya `
    --freeze-encoder --epochs 10 --micro-batch 4 --grad-accum 8 --lr-head 3e-4 `
    --early-stop-metric composite

# 3) 评测（三个划分 + 逐条结果，逐条结果是为了能做配对显著性检验）
& $PY -u -m src.evaluate --ckpt out/run6/final --ds data/ds6 --split test --baseline models/laya_1024
& $PY -u -m src.evaluate --ckpt out/run6/final --ds data/ds6 --split train --limit 800
& $PY -u -m src.batch_predict --ckpt out/run6/final --cases data/ds6/test_cases.jsonl --compare-rule --top 0 --out out/run6/percase_test.jsonl
```

**预计**：约 1.5~2 小时（8~10 轮，每轮约 12 分钟，早停会自动提前结束）。

### Round A 的判定门槛（跑完立刻能判）

| 结果 | 判定 | 下一步 |
|---|---|---|
| AUC ≥ 0.62 **且** route macro-F1 ≥ 0.40 **且** MAE ≤ 0.65 | ✅ 方法修对了 | 进 Round B（上 9951 条） |
| 其中 1~2 项达标 | ⚠️ 部分有效 | 先看"训练集 vs 测试集缺口"：缺口 < 0.05 说明泛化没问题、是任务本身难；缺口 > 0.15 说明还有别的泄漏 |
| AUC < 0.60 或 F1 < 0.30 | ❌ 方法还有问题 | **不加数据**，回去查 state 里还有什么身份线索、以及 review_route 的标签本身是否可达 |

## 四、Round C：如果前两轮还是不够用，就该动任务本身了

**触发条件**：Round B 之后 `review_route` 的 macro-F1 仍 < 0.40，或 AUC 仍 < 0.65。

### C1. 换掉 `review_route` 的标签来源（我认为这是最值钱的一步）

现在的标签是 `src/task.py:route_policy()` 这条**人为规则**算出来的（策略蒸馏）。
它有两个先天问题：语义信息量低、而且"规则边界"和"真实审核难度"根本不是一回事。

**改法**：用 GitHub 真实的 review 事件做标签。有 token（5000 次/小时），
挖 9951 条 PR 的 reviews 大约 1 小时（1 次请求/PR）。
新的四类定义建议：

| 类别 | 判据（都用真实事件） |
|---|---|
| `fast_track` | 合并前 0 条 review 评论，且从创建到合并 < 24 小时 |
| `normal` | 合并，且 1~3 条 review 评论 |
| `needs_tests` | review 里有评论明确要求补测试，或改动含 src 不含 test 且被要求修改 |
| `block` | 出现 `CHANGES_REQUESTED`，或被关闭且未合并 |

改动范围：`mine_github.py` 加 `--with-reviews`（已有）、`task.py` 换 `LabelPolicy.review_route()`。
**其余管线一行不用动**（这是原设计留的口子）。

### C2. 换掉 `will_merge` 的任务定义

"这个 PR 会不会被合并"本身噪声极大（维护者精力、时间、项目策略都影响它），
跨仓库 AUC 的现实天花板我估计在 0.70~0.78。
如果目标是"帮我判断改动风险"，更可靠的重述是**三选一**：

- `merge_as_is`（能直接合）
- `merge_with_changes`（有价值但要改）
- `reject`（该关掉）

这个定义更贴近"代码质量"，而不是"运气 + 仓库政策"。

### C3. 换路线：在目标仓库自己的历史 PR 上微调

如果真实用途是**给你自己的仓库**排风险，那正确做法不是在 49 个别人的仓库上训通用模型，
而是在**目标仓库自己的历史 PR**（几百条起步）上微调 + 校准，
并把"该仓库历史合并率"当成**显式特征**喂进去（而不是让模型去猜）。
这条路的改动量：`mine_github.py` 限定单个仓库 + `build_state` 加一行该仓库的历史先验。
**这条我建议单独排一轮，不要和 C1/C2 混在一起做。**
